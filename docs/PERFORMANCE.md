# 性能报告（demo 实测）

本文所有数字由仓库内置 demo 在本机真实跑出，未做任何人工修改或艺术加工。
换机器、换 Python 版本重跑，延迟类指标会有差异；召回/排序类指标是确定性的（固定 seed），应当一致。

## 复现方式

```bash
pip install -e .
python -m llm_eval_kit.cli demo --out reports
# 等价：llm-eval-kit demo --out reports
```

- 运行环境：Windows 11（10.0.26200）x64，CPython 3.10.9，无 GPU，无网络依赖
- 运行日期：2026-10-02
- 语料：内置 24 段关于 RAG 与 LLM 评测的中文短文（`llm_eval_kit/demo.py`）
- 评测集：规则合成器生成 24 条 query-doc-answer 三元组（seed=42），
  其中含同义改写的困难样本（如「幻觉」→「梦话」）
- 检索深度 top-K = 10，延迟为每次查询 `time.perf_counter` 实测

延迟列为本机实测，机器间差异明显，仅作量级参考；

Recall@1 0.9167 [0.7917, 1.0000]，Recall@10 0.9583 [0.8750, 1.0000]，
MRR 0.9375 [0.8333, 1.0000]，MAP@10 0.9375 [0.8333, 1.0000]，NDCG@10 0.9430 [0.8442, 1.0000]。

上表 demo 评测集无 `grades` 分级标注，报告中的 Weighted NDCG@10 列显示 —
（诚实降级：不计算、不输出 0 冒充），控制台输出与既往版本完全一致。

## JSONL 评测集实测（dataset_demo，2026-10-04）

分级相关度 Weighted NDCG@10 的实测来自 [`examples/dataset_demo.jsonl`](../examples/dataset_demo.jsonl)
（**合成 demo 数据，非人工标注**，`_meta.provenance` 已标注；12 条查询，其中 2 条带
`grades` 分级标注）。复现方式：

```bash
python -m llm_eval_kit.cli --dataset examples/dataset_demo.jsonl --out reports
```

本机实测（2026-10-04，环境同上，bootstrap seed=42）：

| 管线 | Recall@1 | MRR | MAP@10 | NDCG@10 | Weighted NDCG@10 | P50(ms) | P95(ms) |
|---|---|---|---|---|---|---|---|
| bm25 | 0.9583 [0.8750, 1.0000] | 1.0000 | 1.0000 | 1.0000 | 1.0000 [1.0000, 1.0000] | 0.07 | 0.09 |
| tf | 0.9583 [0.8750, 1.0000] | 1.0000 | 1.0000 | 1.0000 | 1.0000 [1.0000, 1.0000] | 0.09 | 0.13 |
| hybrid | 0.9583 [0.8750, 1.0000] | 1.0000 | 1.0000 | 1.0000 | 1.0000 [1.0000, 1.0000] | 0.20 | 0.30 |

解读（如实记录，包括饱和这个事实本身）：

- Recall@1 = 0.9583 而非 1：q010 有两篇相关文档（d01、d12），top-1 只覆盖其中一篇
  （该查询 Recall@1 = 0.5），(11 + 0.5) / 12 = 0.9583；
- Weighted NDCG@10 = 1.0000 是**饱和值**，不说明指标无效：本数据集仅 2 条查询带分级
  （d08 标 2、d12 标 2、d01 标 1），且这些分档文档在三条管线下都排 top-1，
  与理想排序一致；带分级的文档一旦被排低、或 grade-0/1 边界文档参与竞争，
  该指标才会与二元 NDCG 拉开差距（单测中有手算可核的此类用例）；
- 未标注分级的查询按增益 1（二元口径）计入——加权 NDCG 不会因为数据集只有部分
  分级标注而缩小评测范围；
- 这份数据是合成 demo，只用于验证通道连通与口径正确，分级相关度指标的真实价值
  要等人工标注集（见 [datasets.md](datasets.md) 标注指南）落地后才会显现。

## badcase 归因

|---|---|---|---|---|
| bm25 | 1 | 0 | 0 | 1 |

唯一未命中的是改写样本 `什么是梦话？`（原主题词「幻觉」被改写为零词面重叠的表达）——
这正是纯词面检索的教科书式失败案例，归因为「关键词不匹配」。

## LLM-as-judge（MockJudge，n=23）

| 维度 | 平均分 |
|---|---|
| 正确性 (correctness) | 4.8300 |
| 相关性 (relevance) | 5.0000 |
| 可操作性 (actionability) | 1.3000 |
| 清晰度 (clarity) | 4.4300 |

解读：

- demo 的「应答器」是抽取式的（直接返回 top-1 文档原文），与参考答案同源，所以正确性/相关性高；
- 可操作性 1.30 分很低是**真实且合理**的信号——原始文档段落几乎不含步骤词、数字与列表，
  MockJudge 的词面规则正确地识别出了「答案不可操作」；
- 样本数 23 而非 24：唯一未命中的查询检索结果为空，抽取应答器返回空串，该条不参与评分。

## 真实 LLM 裁判验证（2026-10-02）

`OpenAICompatibleJudge` 的真实服务路径已做一次性端到端验证（key 只从环境变量读取，未入库、未出现在任何输出）：

- 端点：阿里云 DashScope OpenAI 兼容模式（`compatible-mode/v1`），模型 `qwen-turbo`
- 输入：demo 风格评测三元组——query「什么是召回率（Recall@K）？」+ 待评答案 + 参考答案
- 真实模型返回四维评分：`correctness=5, relevance=5, actionability=1, clarity=5`
- 真实 rationale：「待评答案准确解释了召回率@K的定义，与参考答案一致，紧扣用户问题，表达清晰，但未提供可操作的步骤。」
- 交叉验证：真实裁判与 demo 中 MockJudge 对「不可操作」类答案的判断方向一致（真实 1 分 vs mock 均值 1.30）

错误路径同日在真实网络下验证：指向无效/未授权端点的调用分别返回 HTTP 307/404/401，均被包装为 `LLMJudgeError` 而非裸异常，与管线的优雅跳过承诺一致。

### OpenAI 官方端点与其他 provider 的实测边界（2026-10-02 补充）

对评审要求补充实测的端点，同日做了真实尝试（key 只用环境变量，输出脱敏）：

| 端点 | 结果 | 说明 |
|---|---|---|
| `api.openai.com/v1`（OpenAI 官方，gpt-4o-mini） | HTTP 401 | 环境 `OPENAI_API_KEY` 并非 OpenAI key（为内部网关 key），官方端点无法在本环境实测 |
| `api.z.ai/api/paas/v4`（z.ai 公网文档路径） | HTTP 401 | 环境 key 未被 z.ai 公网接受 |
| ZCODE/ZAI 网关（环境变量 base URL 及路径变体） | HTTP 307/404/401 | 网关路由契约未知，未取得成功响应 |

结论：OpenAI 兼容协议的真实请求/解析/错误包装路径已由 DashScope 实测覆盖；OpenAI 官方端点缺少可用 key，无法实测——这不是假设，而是上表 401 的实测结果。任何持有对应 key 的人可设 `EVAL_REAL_LLM_SMOKE=1` 与 `EVAL_LLM_*` 环境变量后一键复验（冒烟测试已就绪）。

本轮还据实测发现改进了错误诊断：`LLMJudgeError` 的 HTTP 错误信息现在会带上服务端响应体摘要（如 OpenAI 的 `invalid_api_key`），排障时可直接看到拒绝原因。

HTTP 层由本地真实 socket 集成测试覆盖（`tests/test_judge_real_http.py`：127.0.0.1 服务器 + 完整 urlopen 链路）。仓库测试套件保持全离线；真实冒烟测试默认跳过，设 `EVAL_REAL_LLM_SMOKE=1` 与 `EVAL_LLM_*` 端点环境变量后可随时复验。

## 规模说明

- 本报告仅代表 24 段玩具语料、24 条查询的 demo 规模，不构成对真实业务语料的性能结论；
- 检索器为纯 Python 教学实现，未做向量检索、未做并发，延迟数字不代表生产检索引擎水平；大语料场景另有 `FastBM25Retriever`（见下节实测）；
- 四条管线指标完全相同是语料特性所致：玩具语料中词面重叠即可解决问题，
  语义漂移类困难样本在本语料中只有 top-1 层面的扰动（见 MRR 略低于 1），
  RRF 融合因此与单路、加权融合同分——区分融合策略优劣需要语义类困难样本；

## 大语料基准（FastBM25Retriever，2026-10-04 实测）

`FastBM25Retriever`（`src/llm_eval_kit/fast_retriever.py`）是纯 stdlib 倒排索引版 BM25，
打分公式与 `BM25Retriever` 完全一致（一致性抽检：top-10 文档序列逐一相同、得分差 < 1e-9），
差异只在候选集——玩具版每次查询全量扫描全部文档，快速版只遍历查询词元的倒排表。

### 实测结果（seed=42，单线程，本机 Windows / Python 3.10）

语料：20,000 段合成中文文本（130 万词元，5,000 词元的 Zipf 分布）；查询：100 条、每条 6~14 词元、top_k=10。
查询词元取自词频秩 50~2000（模拟避开近似停用词的真实关键词查询），**倒排扫描量占比均值 4.5%**。

| 实现 | 索引构建 ms | P50 ms | P95 ms | 100 条总耗时 ms |
|---|---:|---:|---:|---:|
| BM25Retriever（全量扫描） | 980 | 23.4 | 28.4 | 2343 |
| FastBM25Retriever（倒排索引） | 978 | **0.6** | **1.0** | 60 |

**查询加速比 40.4x（P50）/ 28.6x（P95）**，索引构建耗时基本持平（同为约 1s）。

### 对照场景：查询被高频词元主导时

同一语料，查询词元秩带放宽到 10~2000（高频词元大量出现，**倒排扫描量占比 85.4%**）：

| 实现 | P50 ms | P95 ms |
|---|---:|---:|
| BM25Retriever（全量扫描） | 42.0 | 54.4 |
| FastBM25Retriever（倒排索引） | 16.1 | 23.2 |

加速比降为 **2.6x / 2.3x**——倒排索引的收益与"查询词元有多稀有"直接相关：
查询命中全库高频词元时，倒排表本身就接近全库扫描。这是算法边界，如实记录。
