# ADR-0002: 大语料检索——纯 stdlib 倒排索引，不引入 rank-bm25

- 状态：已采纳
- 日期：2026-10-04
- 关联代码：`src/llm_eval_kit/fast_retriever.py`、`scripts/bench_large_corpus.py`、`docs/PERFORMANCE.md`

## 背景

玩具 BM25 每次查询全量扫描全部文档，2 万段语料下单查询 P50 约 23ms，
评测集放大后不可用。候选方案：引入 `rank-bm25`（numpy 加速）或自写倒排索引。

## 决策

自写 `FastBM25Retriever`：纯 stdlib 倒排索引（token → 文档倒排表），
Okapi BM25 公式与 `BM25Retriever` 逐项一致，查询只遍历候选文档的倒排表。

不引入 rank-bm25 的理由：
1. 本仓库的卖点是"零网络依赖、离线可跑"，第一个第三方运行时依赖应当为不可替代的能力而付；
2. rank-bm25 底层走 numpy，打分累加路径不同，与玩具版的口径一致性只能靠容差断言；
   自写倒排可以逐项复用同一公式，一致性测试更强（实测 top-10 序列逐一相同、分差 < 1e-9）；
3. CI 无需为 optional extra 改安装矩阵。

## 实测（2 万段 / 100 查询 / seed=42，详见 docs/PERFORMANCE.md）

- 中频词元查询（倒排扫描量 4.5%）：P50 23.4ms → 0.6ms（约 40x）；
- 查询被头部高频词元主导时（扫描量 85.4%）：仅 2.6x——倒排表本身接近全库扫描，
  这是算法边界，如实记录。

## 代价

- 浮点累加次序与玩具版不同（玩具版按 set 迭代序、快速版按排序后词元序），
  一致性断言必须带 1e-9 容差而非逐位相等；
- 仍为单机内存索引，无持久化与并发——生产场景换真实检索引擎的口径不变。
